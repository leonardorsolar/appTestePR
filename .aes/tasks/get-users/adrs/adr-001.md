# ADR-001: Introduzir "usuário" como primeiro domínio de negócio do backend, via GET /users somente-leitura

**Decisão:** Estabelecer "usuário" como o primeiro conceito de domínio real do backend, expondo apenas `GET /users` — leitura completa, sem paginação, sem autenticação, sobre uma lista fixa em memória com dados de exemplo, retornada como array JSON plano com os campos `id`, `nome` e `email`.

## Status

Aceita

## Data

2026-09-10

## Contexto

O `AGENTS.md` deste repositório documenta uma decisão explícita anterior (ADR-001 da fundação `servidor-backend`) de manter o backend mínimo, sem domínio de negócio definido, até que um domínio real fosse necessário — hoje o único endpoint existente é `GET /health`, sem qualquer conceito de entidade de negócio. Não existe banco de dados, ORM, camada de persistência ou diretório de models no projeto.

A solicitação desta PRD é criar um endpoint `GET /users` cuja resposta retorna a lista de usuários. Isso exige decidir, pela primeira vez neste projeto, o que é um "usuário", de onde vêm esses dados, e qual o escopo de operações suportadas — decisões que o ADR-001 da fundação explicitamente deixou em aberto para quando um domínio real surgisse.

## Decisão

1. "Usuário" passa a ser o primeiro domínio de negócio real do backend (confirmado explicitamente pelo usuário nesta sessão de brainstorming, não uma inferência).
2. O escopo desta funcionalidade é somente-leitura: apenas `GET /users` (listagem). Criar, editar ou excluir usuários, e buscar um usuário individual por id, ficam fora de escopo.
3. Os dados vêm de uma lista fixa em memória, com registros de exemplo/demonstração — sem banco de dados ou persistência real.
4. Cada usuário na resposta tem os campos `id`, `nome` e `email`.
5. A resposta é sempre a lista completa, sem paginação, filtros ou busca.
6. O endpoint é público, sem autenticação — consistente com o único endpoint existente (`/health`).
7. O formato da resposta é um array JSON plano (sem envelope de metadados).

## Alternativas Consideradas

### Alternativa 1: Dados de exemplo apenas como placeholder técnico (sem virar domínio de negócio)

- **Descrição**: Endpoint retorna dados fictícios só para demonstrar o padrão de rota, sem representar um domínio de verdade — mantendo o ADR-001 da fundação intacto.
- **Prós**: Preserva integralmente a decisão de escopo mínimo já registrada.
- **Contras**: Não atende ao pedido do usuário, que confirmou explicitamente querer "usuário" como domínio real.
- **Motivo da rejeição**: Usuário confirmou intenção explícita de estabelecer o domínio, na primeira pergunta de esclarecimento desta sessão.

### Alternativa 2: Persistência real (banco de dados) desde já

- **Descrição**: Introduzir um banco de dados (ex. SQLite, Postgres) para armazenar usuários de verdade.
- **Prós**: Caminho mais próximo de um sistema de produção completo.
- **Contras**: Amplia drasticamente o escopo (schema, migrações, camada de acesso a dados) para uma primeira PRD que só pede leitura de uma lista.
- **Motivo da rejeição**: Usuário optou explicitamente por lista fixa em memória, mantendo o esforço mínimo necessário para o objetivo pedido.

### Alternativa 3: CRUD completo (criar/editar/excluir usuários) nesta mesma PRD

- **Descrição**: Incluir `POST`, `PUT` e `DELETE` de usuários junto com o `GET /users`.
- **Prós**: Entrega o domínio de usuário de forma mais completa de uma vez.
- **Contras**: Escopo maior que o pedido original ("cria um método GET /users"); exige decisões adicionais (validação de escrita, concorrência, idempotência) não solicitadas.
- **Motivo da rejeição**: Usuário confirmou explicitamente escopo restrito à leitura; escrita fica como não-objetivo para uma iteração futura.

### Alternativa 4: Resposta paginada ou em envelope com metadados

- **Descrição**: Retornar `{ data: [...], meta: {...} }` com suporte a `page`/`limit`, como é comum em APIs REST de listagem.
- **Prós**: Mais alinhado a práticas de mercado para bases que crescem; evita quebra de contrato se a lista crescer muito.
- **Contras**: Complexidade desnecessária para uma lista fixa e pequena em memória.
- **Motivo da rejeição**: Usuário optou por array plano sem paginação, compatível com o volume de dados desta primeira iteração.

## Consequências

### Positivas

- Desbloqueia o primeiro endpoint de domínio de negócio do backend sem introduzir infraestrutura (banco, auth) não solicitada.
- Mantém consistência com o padrão de rota já estabelecido por `/health` (handler simples, documentado via `@openapi`, sem estado compartilhado entre testes).
- Escopo restrito e explícito reduz superfície de retrabalho nesta primeira iteração.

### Negativas

- Dados de exemplo em memória são perdidos a cada reinício do processo — não há persistência real.
- Ausência de autenticação significa que qualquer cliente pode listar os dados de exemplo; aceitável apenas porque os dados não são sensíveis (exemplo/demonstração) e o padrão já existente do projeto é público.
- Sem paginação, uma base de usuários que cresça muito no futuro exigirá revisão do contrato de resposta.

### Riscos

- Esta decisão estabelece um precedente de domínio que próximas features podem tentar expandir sem nova validação explícita — mitigação: qualquer extensão (escrita, autenticação, persistência) deve passar por nova rodada de esclarecimento, não ser assumida.
