# ADR-002: Dados de usuários inline em routes/users.js, sem módulo de dados ou camada de serviço separados

## Status

Aceita

## Data

2026-09-10

## Contexto

O [ADR-001](adr-001.md) já decidiu, no nível de produto, que os dados de `GET /users` vêm de uma lista fixa em memória, sem banco de dados, com os campos `id`, `nome` e `email`. Falta decidir, no nível técnico, **onde** essa lista vive no código e **como** o handler a expõe, seguindo o padrão já estabelecido pelo único endpoint existente (`GET /health`, em [health.js](../../../../src/routes/health.js)): um arquivo por rota, handler simples, sem camada de serviço, sem diretório de dados/models.

O projeto não tem hoje nenhum diretório `data/`, `models/` ou `services/` — apenas `src/routes/` e `src/docs/`. Introduzir um desses exigiria justificar uma convenção nova para armazenar 3-4 registros fixos que nunca são escritos.

## Decisão

1. A lista de usuários é um array de objetos literal, declarado como constante no topo de `src/routes/users.js` — não há arquivo de dados separado nem camada de serviço.
2. O handler `usersHandler` lê essa constante em memória e responde com `res.status(200).json(users)` — sem transformação, filtro ou cópia defensiva (a lista nunca é mutada por esta funcionalidade, ver [ADR-001](adr-001.md)).
3. O campo `id` de cada usuário de exemplo é um número inteiro sequencial (`1`, `2`, `3`, ...), não uma string — decisão confirmada com o usuário durante a clarificação técnica desta TechSpec.
4. Registro em `app.js` segue exatamente o padrão de `/health`: `app.get('/users', usersHandler)`.
5. A rota é documentada via bloco `@openapi` inline, imediatamente acima do handler, no mesmo arquivo — mesmo padrão de `health.js`.

## Alternativas Consideradas

### Alternativa 1: Módulo de dados separado (`src/data/users.js`)

- **Descrição**: Extrair o array de usuários para um módulo próprio, importado pelo handler em `routes/users.js`.
- **Prós**: Separa dados de rota; facilita reuso caso uma segunda rota precise dos mesmos dados no futuro.
- **Contras**: Introduz uma convenção de diretório (`data/`) que não existe no projeto, para um array de poucos registros que só é lido por um único handler — estrutura para uma necessidade hipotética, não a atual.
- **Motivo da rejeição**: Usuário confirmou explicitamente a opção inline durante a clarificação técnica; consistente com o escopo mínimo do projeto (AGENTS.md, ADR-001 da fundação `servidor-backend`).

### Alternativa 2: Camada de serviço (`UsersService.list()`)

- **Descrição**: Introduzir uma função/classe de serviço entre o handler e os dados, mesmo sem lógica de negócio além de retornar o array.
- **Prós**: Prepararia o código para lógica futura (filtros, paginação, persistência real).
- **Contras**: Camada sem propósito atual — não há lógica a encapsular hoje; viola a restrição do PRD contra "estrutura para features futuras".
- **Motivo da rejeição**: Fora de escopo pelo PRD (Restrições Técnicas de Alto Nível) e pelo ADR-001 da fundação.

### Alternativa 3: id como string (ex. `"u1"`)

- **Descrição**: Usar strings como identificador dos usuários de exemplo, em vez de inteiros sequenciais.
- **Prós**: Evita a leitura de que o id é a posição no array.
- **Contras**: Adiciona uma convenção de formato de id sem motivação do PRD, que só faria sentido se houvesse criação de usuários (fora de escopo).
- **Motivo da rejeição**: Usuário confirmou inteiro sequencial durante a clarificação técnica.

## Consequências

### Positivas

- Mantém `users.js` no mesmo nível de simplicidade de `health.js` — um único arquivo, sem indireções, fácil de revisar e testar.
- Não introduz nenhuma convenção de diretório nova, alinhado ao escopo mínimo documentado em AGENTS.md.
- `id` numérico sequencial simplifica exemplos no Swagger e nos testes (comparação direta com `toEqual`).

### Negativas

- Se uma segunda rota precisar dos mesmos dados de usuário no futuro, a lista precisará ser extraída de `users.js` naquele momento (não há reuso hoje, nem é necessário).
- Sem camada de serviço, qualquer lógica futura (ex. filtro) exigiria refatorar o handler — aceitável, pois lógica futura é explicitamente fora de escopo.

### Riscos

- Nenhum risco técnico relevante identificado: a lista é somente-leitura, não compartilha estado entre requisições, e não há concorrência de escrita a proteger.

## Notas de Implementação

- `users.js` segue a mesma estrutura de `health.js`: bloco `@openapi` JSDoc imediatamente acima do handler exportado.
- `app.test.js` tem asserções de igualdade exata sobre `Object.keys(response.body.paths)` (IT-003) e sobre a lista de endpoints reais — precisam ser atualizadas para incluir `/users` quando a rota for implementada (rastreado em `_tests.md`, não nesta ADR).
